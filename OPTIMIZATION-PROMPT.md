# Промпт для оптимизации «Эффекта бабочки»

Ты работаешь в существующем репозитории транспортного симулятора. Оптимизируй приложение для слабого ноутбука и бюджетного телефона. Вноси изменения, запускай приложение и проверяй результат. Сначала найди узкие места измерениями; каждый этап должен давать проверяемое улучшение. Не обещай отсутствие лагов на любом устройстве.

## Контекст проекта

- Frontend: `frontend/`, Next.js 16, React 19, TypeScript, MapLibre GL JS, Framework7, Motion.
- Backend: `backend/`, FastAPI, NetworkX, PyMongo. Данные и результаты сохраняются в MongoDB.
- Дорожная модель: 468 узлов, 963 направленных участка, 12 исходных направлений поездок. Поиск пути учитывает запреты поворотов. Потоки назначаются за два прохода с формулой BPR.
- Карта дополнительно показывает около 9 тысяч полигонов из `frontend/public/context.geojson` размером около 2,7 МБ и каталог из 2243 парковок. Уточни размеры по текущим файлам.
- Прочитай применимые `AGENTS.md`. Перед изменением Next.js прочитай соответствующую документацию установленной версии в `frontend/node_modules/next/dist/docs/`.
- Запуск описан в README. Если существуют `.local/start.sh` и `.local/stop.sh`, используй их для локального стека. Для сравнения используй production-сборку.

Уже сделано: виртуальный список парковок на TanStack Virtual с измеряемой высотой строк и сохранением фокуса, ленивое монтирование закрытого списка, индекс поиска и отложенная фильтрация; разделены обновления независимых слоёв карты; анимация выключена при открытии, есть экономный режим с pixel ratio 1; включённая анимация ограничена по частоте и количеству маркеров, ожидает обработки предыдущего кадра, останавливает обновления в скрытой вкладке и во время движения камеры; форматтеры чисел переиспользуются. Проверь это по коду и развивай изменения на основании профиля.

## 1. Снять исходные показатели

Запусти приложение и пройди одинаковый сценарий до и после изменений: холодная загрузка, движение и масштабирование карты, открытие панелей, поиск парковок, прокрутка всего каталога, изменение занятости, ползунок количества машин, демо-расчёт, переключение «До / После», личная поездка с парковкой, создание дома и своей дороги, смена темы, включение анимации и переход в фоновую вкладку.

Используй Chrome DevTools Performance/CDP и профили React при необходимости. Запиши длительность задач главного потока, long tasks, задержки конкретных взаимодействий, кадры при движении карты, память, число DOM-элементов, частоту обновлений GeoJSON и размеры сетевых ответов. Измерение requestAnimationFrame само по себе не доказывает частоту реально отрисованных кадров карты.

Сравни одинаковые viewport, данные и настройки. Проверь desktop 1280×800 и mobile 390×844, DPR 1 и 2, CPU throttling 4× и 6×. Отдельно проверь `prefers-reduced-motion`. Запиши версии браузера, режим GPU и прогрев. Программный GPU в headless Chrome и CPU throttling не заменяют проверку на физическом слабом устройстве; обозначь это ограничение. Не сравнивай работающую анимацию с автоматически отключённой без указания этого различия.

## 2. Оптимизировать списки и React

Для больших коллекций держи в DOM видимые строки и небольшой overscan. Маленькие списки из 5–12 элементов виртуализируй только при подтверждённой пользе. Сохрани динамические высоты, клавиатурную навигацию, фокус редактируемого поля, подписи доступности и значения после прокрутки, фильтрации, закрытия панели и повторного открытия. Не заменяй виртуализацию накоплением страниц в DOM.

Отдели частое состояние ввода и наведения от тяжёлых компонентов. Исправь нестабильные зависимости и повторные вычисления. Применяй memo/useMemo/useCallback там, где профиль показывает лишнюю работу. Не делай глубокое сравнение больших GeoJSON на каждом рендере. Поиск должен оставлять ввод отзывчивым. Расчёты исходной нагрузки при движении ползунка должны иметь debounce и защиту от устаревших ответов.

## 3. Оптимизировать карту

Сохрани один экземпляр карты при изменении настроек и переключении панелей. Обновляй только затронутые источники. Замеряй частоту `setData`, стоимость сериализации, обработки worker и отрисовки. Устрани повторную кластеризацию парковок из-за несвязанных изменений.

Отдели статическую геометрию от изменяемых нагрузок. Проверь возможность `feature-state` или обновлений по ID вместо полной передачи геометрии, учитывая API установленной версии MapLibre. Для тяжёлого контекста оцени компрессию, zoom-dependent detail, упрощение исключительно декоративных полигонов и переход к векторным тайлам, если размеры действительно требуют этого. Не упрощай расчётную топологию и запреты поворотов ради скорости отображения.

Экономный режим должен уменьшать стоимость отрисовки: разумный pixel ratio, минимум blur/glow/overdraw, ограниченные декоративные анимации. Частота анимации машин и число маркеров не должны расти пропорционально 10 000 автомобилям. Не накапливай очередь кадров, не создавай GeoJSON заново каждый кадр. Останавливай таймеры и обновления в скрытой вкладке; освобождай listeners, workers и observers при размонтировании. Сохрани SVG-режим без WebGL.

## 4. Проверить сеть и backend

Замерь отдельно сетевую передачу, JSON parsing, расчёт Python и запись MongoDB. Настрой кеширование и сжатие неизменяемых версионированных файлов. Рассмотри разделение лёгких данных интерфейса и полных каталогов, если это уменьшает время до рабочей карты. Сохрани работу локальной схемы без внешних тайлов.

Если расчёты оказываются узким местом, используй ограниченные кеши, корректную инвалидацию по версии данных и настройкам, устранение повторных запросов и подходящую модель выполнения CPU-задач. Проверь конкурентные запросы. Отмена fetch в браузере сама по себе не означает остановку расчёта на сервере. Не вводи бесконечные кеши, потерю результатов или блокировку health-check длительным расчётом.

## 5. Сохранить корректность

Оптимизация не должна менять формулу BPR, число проходов назначения, спрос, направления движения, запреты манёвров, правила привязки, вместимость дорог, расчёт парковки, метрики и формат экспорта. Сравни численные результаты одинаковых сценариев до и после. Не выдавай условные значения за реальные пробки.

Проверь демо, поиск/редактирование парковок, личный маршрут, снос и добавление домов, свои дороги, мобильные панели, темы, уменьшение движения, SVG fallback, ошибки API и сохранение расчёта после перезапуска. Нестабильные или устаревшие тесты разбирай отдельно; не подгоняй корректный расчёт под неверное ожидание.

## Критерии приёмки

- В каталоге из 2243 парковок одновременно смонтировано не более 16 карточек, включая удерживаемую в фокусе строку. Поиск и прокрутка до последней записи работают; введённые значения сохраняются.
- В покое с выключенной анимацией нет периодических обновлений GeoJSON. Изменение погоды не перезаписывает геометрию своих дорог. Изменение дома не пересылает весь каталог парковок.
- В экономном режиме DPR карты не выше 1. Анимация включается явно, не превышает 10 обновлений в секунду и не создаёт параллельных незавершённых обновлений. В скрытой вкладке новых кадров нет.
- Целевые задержки для типичных действий интерфейса — до 200 мс, для движения карты — от 30 реально отрисованных кадров в секунду на выбранном тестовом устройстве. Если цель не достигнута, покажи фактические значения и оставшееся узкое место. Длительность серверного расчёта учитывай отдельно от отзывчивости UI.
- При повторении сценария память выходит на плато после прогрева. Нет накопления экземпляров карты, обработчиков событий, таймеров и DOM-элементов.
- Production build и проверки TypeScript проходят. Функциональные проверки подтверждают сохранение поведения.

В конце предоставь конкретные изменения, команды запуска и проверки, таблицу «до / после» с условиями измерений и артефактами, оставшиеся ограничения и следующую приоритетную работу. Сохрани отчёт в `PERFORMANCE.md`. Не заявляй проценты ускорения без сопоставимого измерения.
