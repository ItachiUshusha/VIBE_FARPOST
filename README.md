# 402x402

Веб-приложение для вайбатона FarPost: перекройте дорогу на Первой Речке во Владивостоке и посмотрите, как изменятся маршруты и нагрузка на соседние улицы.

**Демонстрационная модель. Транспортные потоки условные.** Реальная геометрия OpenStreetMap не превращает условный спрос в прогноз пробок.

## Быстрый запуск

Нужен запущенный Docker Desktop с Linux-контейнерами. Из корня проекта:

```powershell
Copy-Item .env.example .env
docker compose up --build -d
```

Откройте **http://localhost:3000**. В разделе **«Сценарий»** нажмите **«Демо-сценарий»**. На телефоне раздел открывается нижней навигацией; панель можно потянуть вверх или раскрыть нажатием на захват. При первом запуске образы и зависимости загружаются из интернета. Готовый дорожный набор уже находится в репозитории: повторная загрузка OSM не нужна.

Интерфейс обновлён по [промпту редизайна](APPLE-REDESIGN-PROMPT.md): светлая и системная тёмная темы, постоянная карта, боковая панель на компьютере и нижние панели Framework7 на телефоне. Кнопка в шапке переключает тему. Дизайн-система описана в [DESIGN.md](DESIGN.md).

В интерфейсе по умолчанию **1000 условных авто**. Количество можно задать числом от 20 до 10 000, ползунком или готовыми значениями. Нижняя граница включает 20 автомобилей существующего моделируемого дома: **1 житель = 1 авто**. Это общий спрос по 12 направлениям. Карта исходной нагрузки пересчитывается при изменении количества.

## Новые дома: автоматическое распределение машин

При добавлении дома достаточно поставить метку и указать число жителей. Направление выбирать не нужно: одна машина на жителя равномерно распределяется между всеми различными пунктами назначения района (в текущем каталоге их шесть). Например, 40 жителей добавляют всего 40 машин, примерно по 6,67 на направление. Дробные значения — веса транспортного потока. Машины выезжают через ближайший допустимый дорожный узел и следуют по маршрутам с учётом одностороннего движения и запретов поворотов, увеличивая нагрузку на общие улицы у дома.

Пункт назначения, совпавший с выездом дома, исключается: поездка нулевой длины не создаётся. Перекрытие не меняет заданное распределение: недоступная доля попадает в «Не могут доехать». Коэффициент часа пик применяется один раз ко всем поездкам. Уже учтённые в исходном наборе дома и ранее сохранённые расчёты сохраняют свои исходные данные.

API `housing.add[]` требует только `house_id`, `coordinates`, `residents`. Старое поле `terminal_id` временно принимается для совместимости, но не выбирает направление. В `house_changes.added[]` возвращаются `distribution_mode=all_directions`, `destination_count` и `distribution` с долями и ID поездок. Миграция базы не нужна. При откате старого backend нужно одновременно вернуть frontend: старая версия API требует `terminal_id`.

Изменение запущено локально. При осмотре мобильного интерфейса дом на 40 жителей создал шесть направлений с суммарным вкладом 40 авто: общий поток вырос с 1000 до 1040. Владелец утвердил пять правовых документов, локально опубликована редакция `2026-11-14-individual`. Сборка frontend, TypeScript и линтер прошли без ошибок; тестовые наборы по просьбе пользователя не запускались. Реальные OAuth и Метрика этим обновлением не активированы.

## Полосы, снос домов и свои дороги

Расширение от 14 ноября 2026 года собрано и запущено в Docker по запросу пользователя: обновлены frontend и backend, проверка TypeScript внутри production-сборки прошла. **Тесты после этих изменений не запускались.** MongoDB и её постоянный том сохранены. При открытой старой вкладке обновите страницу через Ctrl+F5.

- У дороги, выбранной для перекрытия или сужения, показывается число полос и схема. Сведения извлечены из сохранённой выгрузки OSMnx в `backend/data/road-details-v1.json`; при отсутствии данных выводится «В OSM не указано». Диапазон означает разное число полос на разных частях участка. Эти сведения не подменяют существующую калибровку вместимости дорог.
- **«Снести дом»** на карте выделяет дома, уже учтённые в расчёте. Нажатие на метку или выделенный контур убирает машины жителей; дом можно вернуть в разделе «Жилые дома». В текущем наборе учтён дом на Хабаровской, 26, с условными 20 жителями. Другие здания являются подложкой, их население не выдумывается.
- **«Своя дорога»**: поставьте начало, повороты и конец, нажмите «Готово», задайте название, полосы в каждом направлении, скорость и двустороннее / одностороннее движение. Доступны до пяти дорог, по 2–12 точек, длиной от 10 м до 10 км. Начало и конец соединяются с существующими перекрёстками не дальше 150 м; пересечения с другими улицами не создают дополнительные съезды.
- Дорога участвует в расчёте движения района и личной поездки только в состоянии «После». Граф копируется для конкретного сценария; исходная сеть, её запреты поворотов и другие расчёты не меняются. Вместимость новой дороги — условная вместимость жилой улицы × полосы в направлении; скорость и длина задают время без пробок, далее применяется существующая модель движения и погода.
- В результатах время записано в минутах и секундах, разница — «На … быстрее / дольше». Убраны «рёбра», «веса», «спрос» и коэффициенты из основных пользовательских подписей. Перегруженные участки считаются по уникальным участкам дороги, а число машин без пути показывается отдельно.

API составного сценария принимает `added_roads: [{road_id, name, points: [{lon, lat}], lanes, speed_kmh, two_way}]`. Снимки построенных дорог и их соединений сохраняются в `added_roads` результата, в MongoDB и экспорте JSON. Данные о полосах повторно извлекаются скриптом `scripts/prepare_road_details.py` из существующего `.local/pervaya-rechka.graphml`.

## Подсказки при неверном положении точки

Если А, Б, «Через», выезд из дома или конец новой дороги стоит слишком далеко от подходящей дороги, карта выделяет исходную точку красным и проводит пунктир к метке **«Сюда»**. Видны расстояние и объяснение; камера показывает обе точки. Кнопка **«Переставить сюда»** и сама метка применяют предложенное положение только по нажатию. Для совпавших концов новой дороги предлагается другой перекрёсток, с проверкой допустимой длины. Подсказки работают и на SVG-схеме без WebGL. Обычные ошибки полей и сервера не получают выдуманных координат исправления.

Сведения `snap_nodes` из `/api/map` используют те же ограничения направлений, что и расчёт: А и дом требуют выезда, Б — въезда, «Через» и новая дорога — обоих. При включённой парковке Б может намеренно находиться вне дороги: успешная поездка с пешим участком не считается ошибкой точки. Алгоритм расчёта не менялся; исправление точки не запускает расчёт автоматически.

Для деплоя обновляйте frontend и backend вместе, чтобы клиент получил сведения о допустимых узлах. Новых переменных окружения и миграций не требуется.

Локально 14.11.2026 сборка frontend и встроенная проверка TypeScript прошли. В Chrome просмотрены А, Б, «Через», дом, начало дороги и совпавшие концы; перестановка по кнопке и по метке, 320 px, landscape, далёкая точка и SVG без WebGL. Скриншоты и геометрия метки — `artifacts/point-guidance/`, журнал просмотра — `inspection.json`. Тестовые наборы по указанию владельца не запускались.

## Личная поездка, парковки, погода и дома

Все настройки сочетаются в одном расчёте. Для примера откройте **«Сценарий» → «Мой маршрут» → «Пример маршрута с парковкой»**, выберите погоду и нажмите **«Рассчитать сценарий»**. Результат откроется в своей панели. «Показать поездку на карте» освобождает карту на телефоне; метки и настройки сохраняются при переключении разделов.

- **Мой маршрут.** Поставьте А и Б на карте; добавьте до пяти точек «Через». Их можно перетаскивать, выбирать заново, менять местами стрелками и удалять. А привязывается к узлу с выездом, Б — со въездом, «Через» — с обоими, в пределах 150 м. Привязки одинаковы до и после, а поиск сохраняет входящее ребро и индекс следующей точки. Поэтому промежуточная точка не отменяет запрет поворота.
- **Парковки.** Каталог содержит 2243 реальных объекта `amenity=parking`, загруженных из OpenStreetMap по всей области дорожного графа. Выдуманных точек нет. У каждой парковки сохранены OSM ID, исходные теги и ссылка на объект; явно частные и запрещённые парковки исключены. Для безымянных объектов подпись составлена по ближайшей улице. В панели доступны поиск и загрузка следующих карточек. Занятость задаётся для сценария от 0% до 100%. Автоматический выбор минимизирует полное время среди достижимых парковок в радиусе 500 м от Б; равенство разрешается по ID. Ручной выбор сохраняет один ID в обеих фазах.
- **Время с парковкой.** `T = дорога + поиск места + пешком`. Для доли занятости `p < 1` поиск занимает `min(900, 60 × p / (1 − p))` секунд. При 100% мест нет. Если парковки рядом не найдены, заполнены, недоступны или выбранная парковка слишком далеко, строится самостоятельный автомобильный маршрут до Б с отдельным предупреждением. Его итог включает только дорогу; поиск места и пеший путь имеют значение `null`. Если в одной фазе парковка включена, а в другой нет, процентная разница не рассчитывается. Пеший путь оценивается по прямой со скоростью 4,5 км/ч и отмечается отдельной пунктирной линией. Личная поездка не добавляет вес в транспортный поток.
- **Погода.** До изменения — сухо. После — сухо, дождь или снег с коэффициентами скорости 1,00 / 0,85 / 0,70. `t_free = length_m / (speed_kmh × k_weather / 3.6)`, затем применяется та же двухпроходная модель BPR.
- **Дома.** На карте размечен существующий жилой дом: Хабаровская улица, 26, координаты из OSM, условные 20 жителей и 20 авто в группе `trip-07`. Нажмите **«Добавить дом» → на карту**: сразу появится метка и карточка настройки. Задайте жильцов и пункт назначения; отдельного подтверждения добавления не требуется. Метку можно перетаскивать, нажимать для повторного редактирования, переставлять через карточку и удалять. 40 жителей дают 40 авто в отдельной группе со стабильным ID. Изменения действуют только в текущем сценарии.

При выборе общего количества авто масштабируется фон, вклад существующих домов сохраняется. При 1000 авто удаление размеченного дома даёт 980, добавление дома на 40 жителей — 1040 до коэффициента часа пик. В каталоге отдельно хранится `source_vehicle_count: 1`: доля этого дома в старой калибровке нужна для выделения фоновых пропорций; фактический вклад теперь равен числу жильцов. Дорожные ёмкости приведены к опорным 1000 авто и остаются фиксированными при изменении количества. Рост спроса повышает `q/C`.

Все параметры находятся в `backend/data/scenario-catalog-v1.json`: радиусы, скорость ходьбы, поиск парковки, коэффициенты погоды, `k_auto`, пределы и опорный спрос. Это демонстрационные параметры, не измеренные значения реального трафика или занятости.

Новый результат также содержит `trip_demand`: разложение каждой группы на фон и вклад домов до/после, исходные веса сравнения и итоговые веса после часа пик. `applied_settings` сохраняет фактически применённые α, β, пороги, множители и параметры парковки.

**Совместимость:** прежние запросы на расчёт принимаются, без количества используется общий спрос 38 авто. Новый каталог `city-scenarios-v2` перераспределяет его с учётом правила «1 житель = 1 авто», поэтому новые численные результаты отличаются от первой версии. `GET /api/baseline?vehicle_count=1000` возвращает выбранный масштаб. Старые записи MongoDB читаются без пересчёта. Локальные каталоги, коэффициенты, привязки, геометрии, предупреждения о парковке и разбивка времени сохраняются в новых результатах и JSON.

## Что работает

- Интерактивная карта MapLibre с реальными дорогами, локальными зданиями и подписями.
- Выбор участка, направление, длина, число полос по OSM, скорость без пробок и загруженность. Белая линия отмечает выбор, красный пунктир — перекрытие.
- Готовый сценарий на Хабаровской улице: закрываются конкретные рёбра обоих направлений одного участка.
- Расчёт на FastAPI/NetworkX, переключение «До / После», время и длина поездки, перегруженные участки и машины без маршрута. Разница показана словами.
- Участки, где добавилось больше всего машин; нажмите строку, чтобы найти дорогу на карте.
- Снос учтённого дома, рисование своей дороги с полосами и скоростью, сравнение времени поездки после совместных изменений.
- Список поездок: нажмите маршрут для показа его полной геометрии и точек А/Б.
- Сброс к исходному состоянию, обработка ошибок, блокировка повторного запуска, выгрузка полного результата в JSON.
- Сохранение запусков в MongoDB и чтение после перезапуска API.
- Интерфейс на русском, адаптация к телефону: панель управления располагается под картой.

Реализованы расширения P1: движущиеся маркеры с паузой, наклон камеры, частичное снижение пропускной способности, условный час пик и **шаблонное объяснение по сохранённому расчёту**. Внешний LLM/GPTunnel не подключён; `/api/analyze` честно возвращает `source: template` и работает без ключа и интернета.

## Данные и география

`backend/data/pervaya-rechka-v1.json` — версионированный, полностью подготовленный набор:

- центр `[131.89965, 43.13272]`: пересечение Океанского проспекта и проспекта Острякова, кольцо Первой Речки;
- автомобильная сеть OSMnx `network_type="drive"`, область примерно 4,4 × 4,4 км;
- 468 узлов, 963 направленных ребра, 12 фиксированных поездок общим весом 38 условных автомобилей;
- геометрия WGS84 в порядке `[долгота, широта]`, исходные OSM ID, направления и отдельные параллельные рёбра;
- явные группы `segment_id → edge_ids`; встречные рёбра объединяются только при совпадении геометрии и исходных OSM ways;
- 149 запрещённых переходов из 133 применимых OSM-отношений поворотов;
- настройки скоростей, условных пропускных способностей, BPR-коэффициентов и порогов нагрузки;
- подготовленный сценарий и результат его автоматической проверки.

Снимок данных получен 13 ноября 2026 года. Направления кольца и объезда проверены по исходному графу, а маршруты — на непрерывность, запрещённые переходы и отсутствие закрытых рёбер. Это проверка данных OSM, не натурное обследование дороги. Условные ограничения, ограничения с `via-way`, временные знаки и не внесённые в OSM запреты не моделируются. Скорости из OSM либо таблицы конфигурации; пропускная способность и спрос не калиброваны.

Локальный контекст (`frontend/public/context.geojson`) содержит 9381 полигон зданий, водоёмов и зелёных зон. Он не участвует в расчёте. По умолчанию используется локальная схема, внешняя подложка OpenStreetMap включается в слоях по желанию. Атрибуция OSM остаётся и без внешних тайлов. Лицензия геоданных: [OpenStreetMap ODbL](https://www.openstreetmap.org/copyright). Шрифт Manrope распространяется по OFL; текст лицензии лежит рядом с файлами шрифта.

## Импорт в MongoDB

При первом старте API проверяет активную версию и импортирует её автоматически (`AUTO_SEED=true`). Для явного повторного импорта:

```powershell
docker compose exec backend python -m app.seed
```

Импорт проверяет ссылки поездок, узлов, сегментов, рёбер и ограничений. `datasets._id` — версия набора, `scenario_presets._id` — устойчивый ID сценария. Используется upsert: повторный импорт не создаёт копии и не удаляет расчёты. После замены набора вручную перезапустите API, чтобы обновить его расчётный кэш:

```powershell
docker compose restart backend
```

Коллекции:

| Коллекция | Содержимое |
| --- | --- |
| `datasets` | Дорожная сеть, конфигурация, поездки и сегменты по версии |
| `scenario_presets` | Готовые сценарии для версии набора |
| `simulation_runs` | Вход, версия, UTC-время создания и полный результат каждого запуска |

## Как считается результат

1. Базовое время ребра: `t₀ = length_m / (speed_kmh / 3.6)`.
2. Для текущего запуска исключаются только `edge_ids` выбранной группы. Исходный граф не изменяется.
3. Дейкстра строит пути по `t₀`. Путь хранит конкретные ID рёбер; при равной стоимости порядок устойчив по ID. Состояние поиска учитывает входящее ребро в узлах с запретом поворота.
4. Поток `q` — сумма весов проходящих поездок. Веса обновляются: `t = t₀ × (1 + 0.15 × (q/C)⁴)`.
5. Выполняется ровно один повторный поиск пути. По итоговым маршрутам заново считаются поток и время рёбер; время поездки суммирует именно эти итоговые времена.
6. Недостижимые поездки возвращаются со своим ID и весом, без геометрии маршрута.

Нагрузка: `< 0.7` — низкая, `0.7–1.0` — повышенная, `≥ 1.0` — высокая. Значения находятся в `config` дорожного набора.

Сравнение средних включает только поездки, достижимые **в обоих** состояниях, с весами **базового** спроса. Сопоставленные количество и вес отображаются отдельно. Нет сопоставимых поездок — средние и дельты `null`; нулевая база — процентная дельта `null`. Интерфейс показывает `—`. Для часа пик используются те же OD-пары с увеличенными весами; изменение спроса явно указано.

## Аккаунты, администрирование, аналитика и публикация на сервере

Это единая инструкция по новым подсистемам. В репозитории изначально не было аккаунтов и документов. Добавлены вход по логину/паролю, подготовленные серверные OAuth-потоки Яндекс ID и VK ID, кабинет, роли `user/admin`, админка, cookie-баннер и маршруты правовых страниц. Реальные приложения провайдеров, счётчик, домен, кабинеты Вебмастера и Search Console **не созданы и не активированы**: доступов и реквизитов владельца нет. Не подставляйте чужие client ID и номера счётчиков для проверки.

### 1. Окружение и сервер

Полный шаблон — `.env.example`. Создайте `.env`, ограничьте чтение (`chmod 600 .env`) и храните его вне Git. Для локального запуска используйте один адрес в браузере: `PUBLIC_ORIGIN=http://localhost:3000`. `localhost` и `127.0.0.1` имеют разные cookie; при выборе другого адреса измените `PUBLIC_ORIGIN` и зарегистрированные callback вместе. `NEXT_PUBLIC_API_URL` оставьте незаданным: браузер работает с `/api` на том же origin через Next.js.

| Переменная | Назначение |
| --- | --- |
| `PUBLIC_ORIGIN` | Единственный адрес приложения с протоколом и портом, без пути. Публичный сервер требует HTTPS. |
| `MONGODB_URI`, `MONGODB_DATABASE` | MongoDB; в Compose адрес внутреннего сервиса задаётся конфигурацией контейнера. |
| `SESSION_DAYS` | Срок сессии, 1–30 дней, по умолчанию 7. |
| `REPORT_TIMEZONE` | Для текущего интерфейса оставьте `Asia/Vladivostok`: выбранный период и подписи рассчитаны на UTC+10. |
| `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` | Приложение Яндекс ID. Секрет получает только backend. |
| `VK_CLIENT_ID` | Web-приложение VK ID с OAuth 2.1 и PKCE. В реализованном потоке секрет приложения не используется. |
| `METRICA_COUNTER_ID` | Публичный номер счётчика; должен быть одинаковым в backend и frontend. Пустое значение полностью отключает загрузку счётчика. |
| `METRICA_READ_TOKEN` | Серверный OAuth-токен с `metrika:read`; не передаётся в frontend. |
| `METRICA_REGISTRATION_GOAL_ID`, `METRICA_LOGIN_GOAL_ID`, `METRICA_SIMULATION_GOAL_ID` | Числовые ID созданных целей для API отчётов. Они отличаются от строковых JS-идентификаторов ниже. |
| `ANALYTICS_UTM_ALLOWLIST` | JSON с разрешёнными значениями `utm_source`, `utm_medium`, `utm_campaign`. Значения вне списков не передаются. Используйте названия каналов/кампаний без данных пользователей. |
| `LEGAL_PUBLICATION_MODE` | `auto` (по умолчанию) публикует утверждённый комплект из поставки; `disabled` отключает публикацию; `manual` использует старые переменные ниже. |
| `LEGAL_PUBLISHED`, `LEGAL_VERSION` | Применяются только при `LEGAL_PUBLICATION_MODE=manual`: явное включение и точная версия утверждённого комплекта. |
| `SEO_INDEXING_ENABLED` | Индексация публичного HTTPS-домена. Для локальной разработки и тестового окружения — `false`. |
| `GOOGLE_SITE_VERIFICATION`, `YANDEX_SITE_VERIFICATION` | Выданные владельцу значения meta-подтверждения, без HTML-тега целиком. |
| `SITE_DOMAIN` | Домен без схемы для `compose.production.yaml`, например фактически принадлежащий владельцу домен. |

На сервере нужен Docker с Compose, домен с A/AAAA-записями на сервер и доступные порты 80/443. `compose.production.yaml` — отдельная полная конфигурация: наружу выходит Caddy, frontend/backend/MongoDB остаются во внутренней сети. Caddy получает сертификат для `SITE_DOMAIN`. `PUBLIC_ORIGIN` в обоих приложениях устанавливается в `https://SITE_DOMAIN`. Не запускайте production-конфигурацию одновременно с локальной на одном Compose-проекте. Нужен отдельный сервер или изолированное окружение для staging.

```bash
docker compose -f compose.production.yaml config --quiet
docker compose -f compose.production.yaml up --build -d
docker compose -f compose.production.yaml ps
docker compose -f compose.production.yaml exec backend python -m app.manage callbacks
```

На машине разработки используются прежний запуск либо `.local/start.sh`, если он существует. После изменения `.env` перезапустите frontend и backend. В локальном запуске Python нужны `PYTHONPATH=backend` и рабочая директория корня репозитория. Убедитесь, что ни reverse proxy, ни инфраструктурный сборщик журналов не сохраняют query OAuth callback, Cookie, Authorization и Set-Cookie. Backend очищает query приватных API в access-log, Next.js обрабатывает callback отдельным маршрутом без логирования URL при ошибке. В Caddyfile access-log не включён.

### 2. Миграция и первый администратор

Перед обновлением сделайте защищённую резервную копию MongoDB, `.env`, утверждённых документов и запишите теги текущих образов. Новый код не удаляет существующие наборы и расчёты. Идемпотентная миграция `accounts-v1` запускается при старте backend; её можно выполнить явно:

```bash
docker compose -f compose.production.yaml exec backend python -m app.manage migrate
docker compose -f compose.production.yaml exec backend python -m app.manage create-admin --username owner
```

Последняя команда интерактивно запросит пароль дважды. Публичного bootstrap-endpoint и пароля по умолчанию нет. Локальный вариант:

```bash
PYTHONPATH=backend .venv/bin/python -m app.manage migrate
PYTHONPATH=backend .venv/bin/python -m app.manage create-admin --username owner
```

Команда не перезаписывает существующий аккаунт. Для уже зарегистрированного владельца сначала установите его ID по записи в базе/деталям пользователя, затем подтвердите этот ID повторно:

```bash
PYTHONPATH=backend .venv/bin/python -m app.manage set-role --user-id USER_ID --confirm-user-id USER_ID --role admin
```

Понижение роли выполняется той же командой с `--role user`; последний активный администратор защищён. Сброс забытого локального пароля: `manage reset-password --user-id USER_ID --confirm-user-id USER_ID`, новый пароль вводится скрыто. Для автоматизации есть `--password-stdin`; не передавайте пароль аргументом командной строки. Не публикуйте локальные `.local/first-admin.txt` и QA-fixture, если они созданы при настройке.

Коллекции: `users`, `identities`, `sessions`, `oauth_flows`, `pending_links`, `auth_limits`, `auth_events`, `audit_log`, `schema_migrations`. Уникальны логин, необязательный email, пара `provider+subject` и пара `user_id+provider`. Сессии хранят SHA-256 от случайного opaque-токена, пароли — scrypt с отдельной солью. TTL-индексы очищают временные записи; при каждом обращении срок дополнительно проверяется кодом. Все административные API и серверная страница `/admin/...` проверяют действующую роль. Блокировка завершает сессии. Права администратора нельзя снять через публичную панель; значимые действия журналируются до изменения со статусом выполнения.

### 3. Яндекс ID и VK ID

Поддерживаемые локальные callback-контракты:

| `PUBLIC_ORIGIN` | Яндекс ID | VK ID |
| --- | --- | --- |
| `http://localhost:3000` | `http://localhost:3000/api/auth/oauth/yandex/callback` | `http://localhost:3000/api/auth/oauth/vk/callback` |
| `http://127.0.0.1:3000` | `http://127.0.0.1:3000/api/auth/oauth/yandex/callback` | `http://127.0.0.1:3000/api/auth/oauth/vk/callback` |

Production-адрес до получения домена не существует. После настройки домена точные полные URL напечатает `manage callbacks` **в контейнере выбранного окружения**. Это `https://SITE_DOMAIN/api/auth/oauth/yandex/callback` и `https://SITE_DOMAIN/api/auth/oauth/vk/callback`, без завершающего `/`, без query. Значения нужно скопировать из вывода команды, а не регистрировать шаблон `SITE_DOMAIN`. Для другого окружения используйте отдельные приложения и соответствующий `PUBLIC_ORIGIN`. Если кабинет провайдера не принимает HTTP callback для локальной разработки, используйте выделенный HTTPS-домен разработки, направленный на приложение; реальные ограничения кабинета требуют проверки владельцем.

Яндекс: откройте [Яндекс OAuth](https://oauth.yandex.ru/), зарегистрируйте приложение для веб-сервиса, укажите реальное название, домен и опубликованные правовые ссылки, добавьте Redirect URI из команды. Выберите только `login:info`, без `login:email`, телефона и даты рождения. Запишите ID и секрет в серверное окружение. Реализация использует authorization code, `state`, PKCE `S256`, обмен на `https://oauth.yandex.ru/token` и профиль через `https://login.yandex.ru/info` с токеном в Authorization. [Документация Яндекс ID](https://yandex.ru/dev/id/doc/ru/codes/code-url).

VK: откройте [кабинет VK ID](https://id.vk.ru/about/business/go), создайте Web-приложение, задайте фактический базовый домен и доверенный Redirect URL из команды, разрешите приложение для нужной аудитории после проверки кабинетом. Запрашивается только `vkid.personal_info`, без телефона и email. `VK_CLIENT_ID` задаётся в backend. Используются текущий домен `id.vk.ru`, authorization code, PKCE `s256`, `state`, обязательный `device_id`; обмен на `/oauth2/auth`, профиль через `/oauth2/user_info`. Проверяются callback-state и state ответа token endpoint, ID профиля сопоставляется с ID token-ответа. Сверка выполнена с [официальным исходным кодом SDK](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts) и его [текущими доменами](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/constants.ts). Сам SDK в браузер не загружается.

Первый вход создаёт пользователя с детерминированным внутренним ID для провайдера; повторный находит уникальную identity и создаёт обычную сессию приложения. Отсутствие email допустимо. При совпадении email можно войти в существующий аккаунт и подтвердить привязку либо явно создать отдельный аккаунт через подтверждённый внешний профиль, без присвоения чужого email и без слияния. В `/account` можно начать привязку к своему аккаунту; необходим вход не старше 10 минут, затем отдельная кнопка подтверждения. Callback одноразовый, ограничен 10 минутами и привязан к HttpOnly-cookie браузера. Принятая редакция условий фиксируется; при её смене до завершения регистрации требуется новое подтверждение. Токены провайдера не сохраняются. Отмена, просроченный/повторный callback, ошибка провайдера и конфликт имеют отдельные сообщения.

Полные тексты и перечень вопросов владельцу находятся в [комплекте для утверждения](backend/legal/OWNER-REVIEW.md). Подготовлены пять документов: правовая информация, оферта о бесплатном сервисе, политика конфиденциальности, политика cookie и отдельное согласие на аналитику. Фактические реквизиты из сообщения владельца сохранены в `backend/legal/operator.json`: Игнат Алексеевич, физическое лицо, amanewave@gmail.com, Россия, сервер во Владивостоке. ИНН, полный адрес и название хостинга не выдуманы. Условия хранения и ручного исполнения запросов отражают реализацию; автоматического удаления аккаунтов по неактивности нет.

До публичного сбора данных владелец подтверждает оставшиеся сведения и обязательства из `OWNER-REVIEW.md`, в том числе инфраструктуру, обработчиков, порядок удаления и уведомления Роскомнадзора. Документы находятся вне public-каталога и не публикуются до явного утверждения.

```bash
PYTHONPATH=backend .venv/bin/python -m app.manage legal-template --output .local/legal-review-402x402.json
# Прочитайте все пять текстов в JSON и OWNER-REVIEW.md; внесите подтверждённые сведения.
# Следующую команду выполняют только после утверждения владельцем:
```

`legal-template` не перезаписывает существующий файл: для следующей редакции укажите новый путь. Текущий комплект владелец уже утвердил: `backend/data/legal-approved.json` поставляется через Git и Docker `COPY data ./data`. В нём только публичные тексты, сведения владельца и отметка утверждения. Секретов в файле нет; черновики из `backend/legal/drafts` сами по себе не публикуются.

Публикация теперь по умолчанию работает в режиме `LEGAL_PUBLICATION_MODE=auto`: backend читает полную утверждённую поставку и берёт редакцию из `version` её JSON. Старые серверные `LEGAL_PUBLISHED=false` и пустая или устаревшая `LEGAL_VERSION` в этом режиме не блокируют документы. `/api/site/config`, регистрация, OAuth и cookie используют фактически опубликованную редакцию. Изменять серверный `.env` для этого исправления не требуется.

Для обновления на сервере передайте весь коммит, включая JSON документов, затем пересоберите и пересоздайте **backend и frontend**:

```bash
# Обычный compose.yaml, в том числе за внешним nginx:
docker compose up -d --build backend frontend
# Вместо предыдущей команды для стека compose.production.yaml:
# docker compose -f compose.production.yaml up -d --build backend frontend
```

Одного `git push` без настроенного автоматического деплоя недостаточно для обновления уже запущенных контейнеров. Данные MongoDB и постоянные тома удалять не нужно. Без Docker перезапустите backend и обновите production-сборку frontend действующим способом запуска проекта.

Режим `LEGAL_PUBLICATION_MODE=disabled` служит для явного отключения публикации. Для прежнего ручного управления задайте `LEGAL_PUBLICATION_MODE=manual`, `LEGAL_PUBLISHED=true` и точную `LEGAL_VERSION` из утверждённого JSON. Эти режимы одинаково поддерживаются при локальном запуске и обоими Compose-файлами. `manual` с неверной версией и `disabled` закрывают публичную регистрацию и согласие на аналитику.

После деплоя проверьте `/api/site/config`: ожидаются `legal_published: true` и `legal_version: 2026-11-14-individual`. `/api/legal/privacy` должен вернуть `published: true` и полный `text`. Откройте `/legal`, `/offer`, `/privacy`, `/cookies`, `/analytics-consent`; затем примите cookie, обновите страницу, откройте настройки и отзовите согласие. Если API недоступен, интерфейс показывает ошибку загрузки и повторную попытку; она отличается от статуса неопубликованного документа.

Для следующих изменений утвердите новый комплект с новой версией через `approve-legal --confirm-reviewed`, включите JSON в коммит и поставку backend. Версию больше не нужно дублировать в окружении для режима `auto`. Для отката публикации используйте `LEGAL_PUBLICATION_MODE=disabled` и пересоздайте backend; для возврата к прежнему комплекту восстановите согласованный JSON и пересоздайте backend. Не подменяйте текст при неизменной версии.

До утверждения `/legal`, `/offer`, `/privacy`, `/cookies`, `/analytics-consent` показывают статус подготовки; неопубликованные документы не включаются в sitemap. Публичная регистрация и первый OAuth-вход закрыты, локальный режим доступен. Старый комплект только из трёх документов после обновления не считается полным: подготовьте и утвердите новую редакцию с cookie и согласием. Простое изменение флага без полного комплекта не открывает регистрацию.

Баннер имеет кнопки «Принять» и «Только необходимые»; выбор меняется через «Настройки cookie» в подвале. «Принять» доступна после загрузки настроек при опубликованных документах и ссылается на отдельное согласие. При ошибке есть кнопка повторной загрузки; «Только необходимые» работает независимо от доступности API. Выбор хранится 180 дней в `fp_consent_v1` и cookie `fp_analytics`, вместе с редакцией правовых документов; новая редакция или старый формат требуют нового выбора. Даже при настроенном счётчике аналитика не запускается без опубликованного комплекта, совпадающей версии и согласия. При отказе необходимые функции продолжают работать.

До согласия iframe отсутствует. При отзыве он отключает сетевые транспорты, включая unload-beacon, затем удаляется; доступные `_ym_`-cookie и записи очищаются. Уже переданные данные нельзя отозвать из сети. Основные cookie: `fp_session`, `fp_csrf`, `fp_oauth`, `fp_link`, `fp_analytics`; на HTTPS сессионные cookie Secure/HttpOnly/SameSite=Lax.

После деплоя откройте все пять ссылок из футера и навигации документов на мобильном и компьютере. Проверьте реальные тексты и версию, отсутствие документов в sitemap до публикации, блокировку «Принять» до неё, повторный выбор после смены версии и отсутствие запросов Метрики при отказе и отзыве. Метрика, OAuth и поисковые кабинеты от публикации документов сами не включаются; их подключение описано ниже.

### 5. Яндекс Метрика и цели

Создайте счётчик на [metrika.yandex.ru](https://metrika.yandex.ru/), задайте фактический домен и часовой пояс Владивостока. Не добавляйте стандартную вставку параллельно: её уже заменяет consent-интеграция. Отключите Вебвизор, автоматические цели и расширенный сбор данных в кабинете, не включайте дополнительные теги через Тег Менеджер. В коде выключены карта кликов, автоматические внешние ссылки, hash и автоматический первый просмотр (`defer:true`); просмотры отправляются вручную один раз на изменение маршрута Next.js. [Параметры счётчика](https://yandex.ru/support/metrica/ru/code/counter-initialize), [hit](https://yandex.ru/support/metrica/ru/objects/hit).

Создайте три цели типа **JavaScript-событие** с точными идентификаторами:

| JS-идентификатор | Когда отправляется |
| --- | --- |
| `registration_success` | Успешное создание аккаунта после одноразового получения результата входа. |
| `login_success` | Успешный повторный вход. Смена пароля не создаёт дополнительную цель входа. |
| `simulation_success` | API успешно рассчитал и сохранил сценарий; ошибка расчёта цель не вызывает. |

Передаётся только фиксированный способ входа `local/yandex/vk`, без user ID, имени, email, токенов и координат. При отказе событие не отправляется и не откладывается до будущего согласия. Введите номер счётчика в `METRICA_COUNTER_ID` для обоих сервисов. Числовые ID созданных целей скопируйте в соответствующие `METRICA_*_GOAL_ID` для отчётов.

Для чтения отчётов получите отдельный серверный токен `metrika:read` и доступ к счётчику; запишите в `METRICA_READ_TOKEN`. Админка → «Источники и конверсии» показывает реальные данные API за период или честный статус подключения со ссылкой на Метрику. Токен в API-ответах и браузере отсутствует. Данные самого счётчика могут появляться с задержкой, фильтры и часовой пояс влияют на результат. Метрика учитывает только визиты с согласием, поэтому её конверсии не обязаны совпадать с полными счётчиками регистраций и расчётов в MongoDB.

UTM принимаются только из `ANALYTICS_UTM_ALLOWLIST`. Например, для настроенных в шаблоне значений: `/?utm_source=vk&utm_medium=social&utm_campaign=launch`. Дополнительные query, hash, email, токены, идентификаторы расчётов и неизвестные UTM не передаются. Для анализа используйте «Отчёты → Источники → Источники, сводка», «Источники → Метки UTM», «Содержание → Страницы входа / Страницы выхода». См. [отчёт UTM](https://yandex.com/support/metrica/ru/reports/tags-utm). Для маршрута регистрации сохраните сегмент с последовательными условиями: просмотр `/register`, достижение `registration_success`, достижение `simulation_success`; повторный вход анализируется отдельной веткой `/login` → `login_success` → `simulation_success`. Условия регистрации и повторного входа нельзя последовательно объединять в одну обязательную воронку. Создание целей и сохранение отчёта выполняются в кабинете после получения доступа; автоматически созданная воронка не заявляется.

### 6. Вебмастер и Search Console

После публикации фактического HTTPS-домена задайте `SEO_INDEXING_ENABLED=true` только для production. `/sitemap.xml` включает каноническую главную и только опубликованные правовые документы. Админка, кабинет, конкретные расчёты, вход, регистрация, API и аналитический iframe в sitemap отсутствуют. `robots.txt` закрывает эти разделы; авторизацию обеспечивают серверные проверки независимо от robots. Локально/staging robots запрещает индексацию всего сайта, sitemap пустой. Canonical не содержит UTM и пользовательские query.

В [Яндекс Вебмастере](https://webmaster.yandex.ru/) добавьте точный HTTPS-адрес сайта. В разделе подтверждения прав выберите meta-тег, скопируйте только `content` в `YANDEX_SITE_VERIFICATION`, перезапустите frontend и нажмите проверку. Затем отправьте `https://ваш-домен/sitemap.xml` в разделе файлов Sitemap. Проверьте статус прав и обработки файла. [Официальная инструкция](https://yandex.ru/support/webmaster/ru/service/rights).

В [Google Search Console](https://search.google.com/search-console) для всего домена выберите Domain resource и добавьте выданную TXT-запись у DNS-провайдера; это предпочтительно при доступе к DNS. Для URL-prefix resource `https://ваш-домен/` можно выбрать HTML tag, перенести `content` в `GOOGLE_SITE_VERIFICATION`, перезапустить frontend и подтвердить. В разделе Sitemaps отправьте `sitemap.xml`, дождитесь статуса успешной обработки и выполните проверку URL главной. [Способы подтверждения](https://support.google.com/webmasters/answer/9008080?hl=ru). Meta-значения не заменяют DNS-подтверждение Domain resource. Не удаляйте токены/TXT после проверки.

До появления домена и входа владельца в кабинеты право собственности и приём sitemap не подтверждены. Локальные проверки XML/robots/meta/canonical не являются проверкой статуса в кабинетах.

### 8. Откат

1. Остановите публичный gateway и пишущие frontend/backend, оставив MongoDB для резервного копирования. Сохраните защищённый архив текущей базы с новыми аккаунтами и приватными расчётами, текущий `.env` и комплект документов.
2. Для возврата к версии **до аккаунтов** восстановите предрелизную резервную копию в отдельную базу, например `farpost_before_accounts`, и направьте старый образ только на неё. Исходную новую базу сохраните закрытой для последующего возврата. Не подключайте старый backend к новой базе: старый API не проверяет владельца сохранённого расчёта и может раскрыть новые приватные результаты.
3. Верните записанные до обновления теги образов и конфигурацию, отключите внешние OAuth ID, `METRICA_COUNTER_ID`, `METRICA_READ_TOKEN`, публикацию через `LEGAL_PUBLICATION_MODE=disabled`, `SEO_INDEXING_ENABLED` до повторной проверки. Не используйте `docker compose down -v` и не удаляйте том `mongo_data`.
4. Убедитесь в правильной выбранной базе, готовности health-check и работе публичной модели до открытия gateway. При возврате на текущую версию восстановите исходный выбор базы, примените идемпотентную миграцию, завершите старые сессии при необходимости и повторите проверку доступа.
